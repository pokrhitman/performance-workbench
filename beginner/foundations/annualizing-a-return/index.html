Annualizing a Return

The last chapter closed on a promise: once sub-period returns are linked into one number, the next question is putting that number on a common yearly footing. That's annualizing. The instinct is to treat it like scaling — a 60-day return times six becomes “the annual rate.” But returns compound, not scale, and that's the exact same lesson the last chapter already proved at a smaller scale. Annualizing is compounding applied to a single number instead of a sequence of them.

Take a portfolio that returns 2.00% over 60 days. Naive scaling multiplies straight through: 2.00% × (365 ÷ 60) 12.17%. Annualize it properly instead — (1.02)^(365 ÷ 60) − 1, exactly what the formula engine's annualize() function computes — and the answer is 12.80%. A real gap, 0.64 percentage points, though not yet an alarming one at roughly two months of data.

Shrink the period without touching the return at all and the picture changes fast. That same 2.00%, earned over just 10 days: naive scaling says 73.00%; annualize() says 106.02%. Same starting number, a 33-point-gap, because the exponent (365 ÷ 10 = 36.5) is now large enough that compounding pulls hard away from a straight-line guess. Ten days of a 2% run is a thin thread to stretch across an entire year.

This is exactly why GIPS — the industry's own performance-reporting standard — explicitly bars compliant firms from annualizing any return for a period under one year, full stop, not just conspiciously short ones. The rule isn't about the arithmetic being wrong; annualize() returns a perfectly well-defined number for a 10-day period. The rule is that the number itself is a simulation — a projection of what twelve months of that exact rate would produce, not a return anyone actually earned.

There's a second choice quietly built into the same formula: what counts as “a year, ” is days. annualize()'s basis parameter defaults to 365 (actual calendar days), but 360 (a banking/money-market shorthand that treats every month as 30 days) and 252 (US trading days, common for equities, since markets aren't open every calendar day) are both real, named conventions — not exotic edge cases. Hold the period and the return fixed and only switch the basis, and the answer still moves: that same 2.00% over 60 days lands at 12.80% on a 365 basis, 12.62% on 360 and just 8.67% on 252. Which basis is “right” isn't a matter of taste — it's set by market convention, the same way choosing Time-Weighted over Money-Weighted Return will be, later in this workbench.

Annualized (Geometric)

  • annualize(periodReturn, periodDays, basis) computes (1 + periodReturn)^(basis ÷ periodDays) − 1 — geometric scaling, never periodReturn × (basis ÷ periodDays).
  • basis is the assumed number of days in a year, not a fixed constant: 365 (actual calendar days), 360 (banking/money-market shorthand) and 252 (US trading days, common for equities) are all real, named conventions that change the exponent — and the answer.
  • GIPS explicitly prohibits annualizing any return for a period under one year in compliant reporting — a sub-annual annualized figure is a projection, not an observed return, regardless of how correctly it's computed.
  • Naive linear scaling doesn't consistently over- or understate the true annualized figure — it understates when stretching a sub-annual period out, and overstates when compressing a multi-year period down. The direction flips at exactly one year.
  • This calculator always takes the period length as elapsed calendar days, whichever basis is selected. A rigorous 30/360 or 252-trading-day calculation would also recount the period itself in that conventions's own units — a refinement this chapter leaves for later.
